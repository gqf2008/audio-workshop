# 批量队列（M4-P1）

> 2026-09-17 首版。对应 thread `cc-ai-audio-workshop-batch-queue`。
> 产品口径：`docs/product-plan.md` §4.2 的 **P1「批量队列」**——「可一次导入 N 篇稿子」。

## 1. 它是什么

一次导入 N 篇稿件（.txt / .md / 无扩展名都行），每篇 = **一个工程**，worker 按顺序
逐篇走与单篇完全相同的那条链路（`load_resumable` → `synthesize` → `assemble`），
每篇产出自己的 `projects/<工程名>/out/final.wav` + `final.srt`。

入口：配音页主操作行「批量…」→ 批量面板（与任务中心同一个锚点，两者互斥）。

## 2. 为什么不是"再写一条合成链路"

批量只是**同一条 `Cmd` 通道上的新命令**（`Cmd::RunBatch`）：

- 稿子正文随命令进 worker（导入期就把文件读进内存）——执行期不再碰用户文件，
  「文件读不到 / 不是 UTF-8 / 空稿 / 重名」这些错误在**导入时**就变成可执行的跳过理由，
  而不是"跑到一半才说文件有问题"；
- 每篇自带 `task_id`，在任务台账里是**独立一条配音任务**：任务中心能看到 N 条、
  排队中的那些能在任务中心**逐条**取消；
- 停止位、取消登记表、进度消息都复用现有那套，没有第二份实现。

## 3. 状态与停止语义（三条别混）

| 动作 | 位置 | 真实语义 |
|---|---|---|
| 停**排队中**的一条 | 任务中心那条的「停止」 | 硬取消：worker 轮到时**不加载模型、不合成**，直接回报跳过 |
| 停**正在跑**的整批 | 批量面板「停止批量」 | 协作停止：当前句合成完就停，后面的篇目不再开（不是"立刻切断请求"） |
| 停**单篇** | 配音页「停止合成」 | 只对单篇那条命令有效；批量里正在跑的那条不在这个槽位里 |

**运行中的批量条目故意不在任务中心给「停止」按钮**：它要停就是停整批，摆一个同名按钮
会让人以为是只停这一条。判定见 `can_stop_task` / `stop_target`（`StopTarget::Batch`
只认 `Pending`）。

停整批时**每一篇都要收到终态**（已完成的算完成，没轮到的逐条报"整批已停止：这篇没跑"）：
worker 不能直接跳出循环——留在台账里的 `Pending` 会让 `tasks_in_flight` 永远为真，
用户之后连单篇都提交不了。有单测钉这条（`stopped_batch_reports_every_item_as_terminal`）。

## 4. 失败、跳过与断点续作

- **跳过**（导入期）：不是文件 / 读不到 / 非 UTF-8 / 空稿 / 超过 2MB / 归一后重名。
  重名必须拦：两个工程同名会写进同一个目录，后一篇覆盖前一篇的产物；判重按
  **大小写归一**比较，因为 macOS / Windows 的文件系统默认不区分大小写
  （`Foo.txt` 与 `foo.txt` 是同一个工程目录）。体积上限按元数据先判，
  误选一个几百 MB 的文件不会先被读进内存。
- **文本清洗**：导入时去掉 UTF-8 BOM、把 CRLF / 单独 CR 统一成 LF——`\r` 留在正文里
  会被念成停顿，而 Windows 导出的 .txt 一定是 CRLF。
- **失败**（执行期）：某篇加载工程失败、服务不可用、拼装失败——**只影响那一篇**，
  后面的照常跑；每篇的行里带上原因，任务中心那条也是失败态。
- **部分失败句**：一篇里有几句失败但成品还是出来了，行里写「已出片 · N 句失败」。
- **断点续作**：重跑同一批，已合成的句子被跳过（`synthesize` 对 `status == "done"` 直接
  continue，因此**零进度回调**）；稿件改了则按未变句文本继承（`reused` 会显示在行里）。
  真机用例 `worker_batch_runs_two_scripts_end_to_end` 就钉这两条。

## 5. 批量导出（P6 的一部分）

批量跑完，成品在各自的 `projects/<工程名>/out/`。导出区的「批量导出」把它一次搬到手：
扫描 `projects/` 下**有成品**（`out/final.wav`）的工程，按当前导出开关（整段 WAV /
逐句 SRT）复制到导出目录，文件名就是工程名（`<工程名>.wav` / `<工程名>.srt`），
完成后状态行报「批量导出：N 篇 → <目录>」，有失败则带上篇数与第一条原因。

几条口径：

- **与单篇导出共用同一份实现**（`src/export.rs` 的 `export_one`）：复制语义、覆盖语义、
  失败文案只有一处。单篇只是"导给当前工程"，批量是"导给所有有成品的工程"。
- **不经过 worker、不进任务台账**：导出只读磁盘上已经拼好的成品（`final.wav` 是
  「临时文件 + fsync + rename」原子写出来的），所以**正在逐句合成**时也能导，也不会
  占用提交守卫——导出期间照样可以开始新的合成。
- **但与单篇拼装/导出互斥**：`assemble` 是先发布 `final.wav`、再写 `final.srt`，
  中间那一瞬扫过去会把正在拼装的工程误报成「缺字幕」；而且两边会往导出目录写同一个
  `<工程名>.wav`。所以单篇拼装/导出在飞时批量导出会拒绝（按钮也一起置灰），批量导出
  在跑时单篇导出也会拒绝。顺带把 `copy_atomic` 的临时文件名改成"进程 id + 自增序号"，
  同一进程里的并发复制不再抢同一个 `.tmp`。
- **顺序确定**：候选工程按工程名（码位序）排序。用 `HashMap` 那种遍历顺序会让
  "同一批文件每次导出顺序不同"，既不好排查也让测试变成碰运气。
- **失败隔离**：某篇缺字幕（勾了 SRT）只让那篇失败并给出「没有字幕文件（out/final.srt）」
  这种能照着做的文案，其它篇照常导出。这种情况**WAV 已经复制过去了**，文案里会写明
  「这条只导出了 WAV」——但整篇仍按失败计（请求的 SRT 没满足），不假装全成。
  没有 `out/final.wav` 的目录**不算候选**，也就不会被算成"导出失败"。
- **工程目录不存在要报错**，不与"目录在但没有成品"共用一句话：前者要用户去看路径/权限，
  后者是「还没跑过配音」。
- **目录名必须是 UTF-8，且不跟符号链接**：`to_string_lossy` 会把两个不同的非法名字
  压成同一个含 `�` 的名字（导出时互相覆盖），所以非 UTF-8 的目录直接跳过并报出来；
  `projects/` 下的符号链接也不跟（否则会把工程目录之外的内容复制出来）。
  扫描期这些"少导了"的问题都会进失败清单，不会静默少导。
- 两个开关都没勾时明确报「未选择导出格式」，且不建导出目录。

## 6. 已知边界

- 队列**不跨进程**：应用退出即清空（与单篇一致）。
- 批量在跑时**仍可编辑当前稿件**（批量写的是别的工程目录，不冲突）；但「开始合成」
  这类提交会被 `tasks_in_flight` 挡住——不排队提交不等于能并发跑同一台 worker。
- 面板与任务中心共用左侧锚点，同时只显示一个。
- 首版没有按篇导出到导出目录：产物在各自工程目录里，批量结束时会在汇总里写出
  成品目录。分轨/批量导出是 P6，另做。
