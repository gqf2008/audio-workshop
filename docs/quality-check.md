# 应用内质检（评估台 v1）

> 2026-09-17。对应 thread `cc-ai-audio-workshop-quality-check`。
> 本文只写**用户能看到什么、数字怎么算、代价是什么**。

## 1. 为什么做

CHARTER §5 把「评估台 `audio-eval`（可懂度/耗时/内存 + 回归对比）」列进免费层，但
它一直只存在于 `tools/audio_eval.py`（M0 命令行）。应用里要判断"这一句合成得对不对"，
用户只能自己听——这正是成功标准第 3 条「5 分钟稿人工投入 < 10 分钟（含校听）」的最大成本项。

现在配音页「高级」里有「质检」：把已合成的句子**逐句交给本地 ASR 回读**，算可懂度并指出
最差的几句，用户直接去重录那几句即可。

## 2. 口径（两种口径别混用）

| 口径 | 出处 | 公式 | 用在哪 |
|---|---|---|---|
| **Levenshtein 可懂度** | CHARTER M0 定标（2/1455 → **99.8625%**） | `1 − 编辑距离 / 参考字数`（字符级） | **应用内质检**（本批实现） |
| 逐例块召回 | `tools/audio_eval.py::recall` | LCS 对齐中连续 ≥2 字匹配块占参考字数比 | M0 评估台的分模型对比表 |

两者数值不可直接比较，文档与界面文案都不做换算。

两侧都先做同一套归一（否则标点、空格、数字读法会变成假错误）：

1. 只保留 CJK / ASCII 字母数字，其余（标点、空白）丢弃，ASCII 转小写；
2. 中文数字串与阿拉伯数字统一（`二零二六` ↔ `2026`、`十七` ↔ `17`、`三点一四` ↔ `3.14`）。
   小数点的处理要一起做：数字之间的 `.` 保留（否则 `3.14` 被清成 `314`，而回读的
   `三点一四` 归一成 `3.14`，会凭空多出 1 个编辑距离——复核实测 66.7%）。

第 2 条规则与 Python 权威实现（`tools/audio_eval.py::normalize_numerals`）
**逐条对照**：夹具 `crates/aw-core/tests/eval_parity_cases.txt` 由
`python3 tools/gen_eval_parity_cases.py` 现场生成（28 条，含「点五/五点」「十/万」「O五/o五」「三点O五（小数尾的字符类不含大写 O）」
这些边界），`cargo test -p aw-core --test eval_parity` 断言一致。
> 这个夹具一共抓到三个移植 bug：「点五」被吞成 `.5`（权威实现里「点」不能起头）、
> 「十七」被拆成「十7」（起头字符类要包含十百千万亿）、
> 「三点O五」被算成 `3.05`（小数尾的数字类不含大写 `O`，权威实现给 `3点05`）。
> 规则漂移靠它挡——加边界用例比读一遍正则有用。

## 3. 用户看到什么

- 入口：配音页「高级」→「质检」（与导出同级；首屏元素数不变，密度红线 ≤8 不破）。
- **回读模型可选**：「高级」→「回读」下拉，候选是**服务清单里 `task == "asr"` 的模型**
  （不是写死的名字；清单加一个就多一项）。默认 `qwen3-asr`（M0 定标同款），选择落
  `settings.json`，重启读回。放在本页而不是全局设置：它只影响配音页的质检
  （归属判定见 `LESSON_全局容器只放全局项单Tab独有的放本页`）。
- **每份分都标着「是谁测的」**：句子除了 `eval_percent` 还有 `eval_model`
  （`project.json` 里能看到），写的是**那一次实际用的回读模型**。它与 `qa-report.md` 里的
  「回读模型」是**同一个入参**（只在 `record_eval_score` 一处写入，
  `qa_report_and_the_project_tag_read_the_same_run_model` 钉住）——所以报告与工程标记
  不可能各说一套。
  换过回读模型后，状态行 **指名道姓** 说出差异，而不是笼统一句"可能是上一个模型测的"：

  ```
  现有 12 句的分数是 fun-asr 测的，当前回读模型是 audio8-asr——换模型会改变质检口径，
  建议重新质检一次再看结论
  ```

  三种情形分开说，这是本批的核心：
  - **来源 = 当前模型** → 「现有 N 句的分数就是 X 测的」（不误报）；
  - **来源 ≠ 当前模型** → 上面那句（两个模型名都点出来）；
  - **旧工程**（本字段引入之前写的，`eval_percent` 有值但没有 `eval_model`）→
    「现有 N 句的分数是【来源未知】的旧记录……无法判断它们是不是 X 测的」——
    既不冒充"匹配"，也不冒充"没测过"（后者是 `eval_percent == None`，压根不进这份统计）。

  一部分重测过、一部分因 ASR 失败沿用旧分时会**两边都报**（"X 测的 M 句；另 N 句来源未知"）。
  分数与来源**同生共死**：重做某句、换词典、换模型导致作废时一起清，落盘也一起落
  （`crates/aw-core/src/dub.rs` 的 `Project::synthesize` 先清后写那条不变式同时管两个字段）。
- 进行中：状态栏「质检中：第 i/N 句」，任务中心一条 `质检` 任务（有进度、可停止）。
- 完成：状态栏 + 任务中心 detail

```
质检完成：平均可懂度 96.4%（57 句）· 最差 第 12 句 92.3%：…质检用【应为 例，读到 力】…
```

「最差」只列**真有差异**的句子（编辑距离 > 0），按可懂度升序取前 3 句，并附首个差异处
±8 字上下文（`diff_snippet`）；一句都没差异就是「全部一致」。

**句子行上也有分数**：选中某句时展开行显示「已合成 · 可懂度 92.3%」，低于 95% 时前面加
`⚠`（`eval_label`；95% 是**启发式提醒**，不是质量门槛——基线是 98.5~100%，留一段余量）。
分数就在「重录」按钮旁边，看到 ⚠ 可以直接点重录。

**质检跑完会直接把最差那句选中**（状态栏补一句「已选中第 N 句」），用户当场就能点旁边的
「重录」。「跳到最差句」按钮会把这句重新选中并滚到列表可见位置，长稿里不必手动翻页。

**排序只改“看”的顺序，不改工程顺序**：只要当前还有有效分数，状态行的
「按分数排序 / 恢复原顺序」和「跳到最差句」就可用。前者按可懂度升序排列 UI 行，
最差句在最前；后者永远按**当前分数**取最低分句，同分取工程 index 最小者，不依赖
上一次质检摘要。重启回灌工程分数后也会重新算出目标，因此修完一句后还能继续排、继续跳。
句子行新增了工程真实下标（`index`），试听、重录、分数回填、状态推进都按这个下标回到
真正的工程句子，行号（`no`）仍只用于显示。排序不会改 `project.json`、不会改时间轴，
全篇试听也仍按工程原序。

**质检报告**：每次质检会在工程目录写一份 `qa-report.md`（原子写）——逐句的「参考 / ASR 回读 /
可懂度 / 首个差异」加汇总（模型、句数、评分句数、转写失败数、平均可懂度）。分数虽然留在
`project.json` 里，但 **ASR 回读原文只有当场才拿得到**，写成文件才能存档、对比两次改稿、或贴进笔记；
完成时的状态栏/任务中心会带上报告文件名。报告与分数都写不进时，摘要里会如实报出来。

**分数跨会话留存**：写进工程 `project.json` 的句级字段 `eval_percent`（`#[serde(default)]`，
旧工程缺这个字段按"没测过"处理）。所以重开应用还能看到上次质检的分数，不必重跑 ASR。
分数**没能写进工程**时（磁盘满/权限等）会如实报「（分数未写入工程：…）」——分数本身仍然有效，
但它下次打开就没了，不能假装存下来了。

两条容易出错的细节（复核抓过，别再踩）：

1. **worker 手里的工程副本要一起更新**：质检把分数写进工程后，worker 持有的 `current`
   也必须是同一份——否则随后的「重录 / 导出（拼装）」会用旧副本再存一次，把刚写下的分数刷掉。
2. **本次 ASR 失败的句子保留旧分数**：失败只说明"这次没测到"，音频没变，旧分数仍然成立；
   摘要里会报「N 句转写失败」。回灌时**只接受状态是「已合成」的句子**——失败句即使文件里
   残留旧分也不贴出来。
3. **顺序就是不变式：先清分并落盘，再写新 wav**。反过来的顺序（写好 wav 再清）会留一个窗口：
   进程在"换完 wav、还没 save"之间退出 ⇒ 磁盘上是**新音频 + 旧分数 + status=done**，重启后
   旧分会贴到新音频上。先清后写让这个组合不可能出现；代价是失败后这句没有分数。
   （这一条被复核推翻过两次：第一版"一开始只在内存里清"会让磁盘留旧分；第二版"成功后才清"
   又有上面那个崩溃窗口。）

分数什么时候失效：

| 动作 | 分数 |
|---|---|
| 该句**开始重做**（重录 / 重跑命中） | 只有那一句作废，并且**立刻落盘**（哪怕后面合成失败）；UI 侧在 `Msg::Sentence` 的 running/done/error 删内存副本；列表回到工程原顺序 |
| 重新合成失败（HTTP 错 / 写盘失败 / 中途退出） | 这句没有分数（旧分已经作废并落盘）——丢一个分数比显示一个错的分数好，重跑质检可补 |
| 改稿 / 载入示例稿 / 清空稿件 / 重新切句 | 全部清空（句子序号与内容都变了） |
| 只改工程名 | **保留**（句子与音频都没变） |
| 续跑时被跳过的已完成句 | 保留（音频没重合成） |
ASR 单句失败（服务端错误）不混进平均分，但在汇总里报出「N 句转写失败」。
**一句都没评上分**时不给"平均 0%"（那是把"没测到"说成"测得差"），单独报
「质检未能评分：N 句 ASR 转写都失败了（检查 ASR 模型/服务）」，并且这条任务在任务中心
标成**失败**（不是绿色的"完成"）——没得出结论不等于质检成功。

质检在飞（含排队中）时**稿件与工程名不可改**：结果按"第 N 句"报出来，改稿会让序号指向
另一句话。质检本身短（N×0.3s 量级），挡一下比给出错位的结论好。

### 3.1 回读模型装不下时怎么办（本机 16 GiB 的真实场景）

`qwen3-asr` 估 3.31 GiB + 1 GiB 余量，本机内存紧时服务直接 503：

```
{"error":{"message":"cannot load model 'qwen3-asr': estimated 3.31 GiB + 1024 MiB
 headroom exceeds available host memory (3.84 GiB)","type":"insufficient_memory"}}
```

这条拒绝不是"这一句没测到"：模型根本加载不了，后面每一句都会同样失败，而客户端还会为
每句白等 5 个退避周期。所以应用**立刻收尾**，并把 503 body 变成一个可执行提示：

```
质检未开始：回读模型 qwen3-asr 装不下：需要约 4.31 GiB（模型 3.31 GiB + 余量 1.00 GiB），
当时可用 3.84 GiB。本机更小的 ASR 模型可选：audio8-asr（权重约 437.7MB）、
fun-asr（权重约 1144.4MB）——在「高级 → 质检回读模型」里改选后重跑。换回读模型会改变
质检口径（audio8-asr / fun-asr 没有词级时间戳与说话人分离），需你确认，本应用不会自动换。
```

判据只有一条（`classify_asr_failure`）：`error.type == "insufficient_memory"` 才算"整轮没戏"；
**模型忙碌也是 503**，那只是这一句没测到，仍旧记一句失败继续跑。

降档候选的排序数字是**磁盘上的权重文件大小**，不是服务的内存估算——两者不是一回事，
所以文案里标的是"权重约 …"，不假装它是内存占用。

## 4. 代价（真机实测，别当成免费）

| 项 | 实测 |
|---|---|
| ASR 调用本身 | 单句 ≈0.2s（`qwen3-asr`，14s 音频的量级见 CHARTER） |
| **首次调用要加载模型** | 本机首次 ≈8s（冷启动那次请求的 wall 时间；之后按句计） |
| 质检后合成会不会变慢 | 未单独量化：引擎 `max_loaded_models: 2`，`qwen3-asr` 与 `audio8-tts` 可能互相挤占。**若你连续"质检 → 合成"发现第一句变慢，就是模型重载**，这是引擎的显存策略，不是质检本身的开销 |

真机锚定（`cargo test -p aw-core --test e2e_service -- --ignored`）：

```
参考: 质检用例：二零二六年共十七人。
回读: 质检用力，二零二六年共十七人。
可懂度 92.3%（编辑距离 1 / 13 字）
```

注意「二零二六 / 十七」两边写法不同但归一后一致 —— 所以那 1 个编辑距离**只**来自
「用例 → 用力」，是真问题（TTS 在这一句上确实读糊了），正是质检要抓的东西。

## 5. 边界与未做

- **不做自动质检**：不挂在合成结束自动跑（会给每轮加 N×0.2s + 模型加载，且用户可能只想听）。
- **没有"一键重录最差句"**：质检跑完会自动选中；点「跳到最差句」只负责滚动定位，
  不会替你按下「重录」（ASR 也可能听错，自动重录等于替用户下结论）。要批量重录需要再动一次列表交互。
- **排序视角不持久化**：排序是当前会话的查看状态，不写工程；重开或重新质检后从工程原序开始。
- **只支持已合成（status=done）的句子**；工程损坏会走 `Project::load_if_present` 的明确报错。
- **换模型不自动作废旧分、也不自动重测**：分数现在**标着来源模型**（`eval_model`），
  界面会指名道姓地说出"这些分是 X 测的、当前是 Y"，但**作不作废由用户决定** ——
  有人就是想拿不同回读模型的结论互相对照，替他清掉等于丢数据。
  旧工程（没有该字段）按**来源未知**显示，不会被当成"就是当前模型测的"。
- **`eval_model` 是"这份分是谁测的"，不是"这份分准不准"**：同一句话换回读模型会得出
  不同数字（词级/说话人能力都不同），所以**不同来源的分数不可直接比较**——
  界面给出提示，但不做换算、也不自动挑一个"更可信"的。
- **不做自动降档**：内存不足时只给"哪个装不下 / 需要多少 / 可用多少 / 换哪个"，
  绝不自动换模型——ASR 一换，质检口径就变了（词级/说话人能力都不同）。
- **回读模型只在配音页的「高级」里**，不进全局设置抽屉（它只影响本页质检）。
- **可懂度不是"发音标准"**：它只回答"ASR 能不能读回你写的字"，读得对但语气差它看不出来。

## 6. 复现命令

```console
cargo test -p aw-core --lib eval::                                   # 口径与边界
cargo test -p aw-core --test eval_parity                             # 与 Python 权威实现逐条对照
cargo test -p aw-core --test asr_mock                                # ASR 请求形状
cargo test -p aw-core --test e2e_service -- --ignored                # 真机（需服务在跑）
cargo test -p audio-workshop --bin audio-workshop -- asr_ memory_shortfall smaller_asr
                                                                    # 选模型 / 报告念实际模型 / 内存不足降档提示
cargo test -p audio-workshop --bin audio-workshop -- qa_source_note eval_model_key eval_ledger
                                                                    # 分数来源：换模型的说明 / 旧工程=未知 / 键名契约
cargo test -p audio-workshop --bin audio-workshop -- --ignored worker_eval_writes_report
                                                                    # 真机：合成 → worker 质检 → qa-report.md，
                                                                    # 且 project.json 的 eval_model 与报告里的模型同源
                                                                    # （真机跑过：模型 audio8-asr，2 句 100%）
AW_UI_STATE=qa-tag cargo run -p audio-workshop                        # 只读演示态：打三条来源口径（不碰用户配置）
python3 tools/gen_eval_parity_cases.py --check                       # 夹具是否过期
```
